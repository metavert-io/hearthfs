# Security guidance: metavert-io/hearthfs

Generated by the Security Steward from `security/threat-model.yaml` (model v1, reviewed at 25f3c03f0205). Edit the model, not this file.

A read-only filesystem view of a Hearthloom brain for agents, mounted on the owner's machine. By design, whatever can read the mount can read the brain's non-private content.

## What this system protects

- C1 The read-only mount (local)
- C2 Brain content served through it
- C3 The Hearthloom key the mount uses
- C4 CI and dependencies

## Assumptions

- A1: Only processes the owner chooses can read the mount; private brain content is never served.

## Keep in mind when changing code

- T-HF-0001 (open, STRIDE:I LINDDUN:data-disclosure ASI02): Any agent given the mount can read and exfiltrate all non-private brain content
- T-HF-0002 (mitigated, STRIDE:T CWE-1357): A dependency from an unknown registry or git source enters the build. Relies on M-HF-0001

## Controls that must stay in place

- M-HF-0001: cargo-deny refuses unknown registries and git sources; locked dependencies (`deny.toml`, `Cargo.lock`, `.github/workflows/ci.yml`)
